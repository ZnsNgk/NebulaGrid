## 1. 本次更新结论

本次检查以新上传的 `NebulaGrid-0523-2.zip` 为准。  
和上一版 2026-05-23 开发日志相比，这一版继续围绕 **任务调度系统生产化收口** 和 **环境安装 worker 化** 推进。

上一版已经进入“GPU 任务调度系统 MVP 阶段”；这一版的关键变化是：

1. **Runtime Guard 不再只是占位**，已经实现远端 PID 树采集、`nvidia-smi compute-apps` 解析、实际 GPU UUID 与分配 GPU UUID 比对，并在连续确认越权后终止任务、标记 `alloc_error`。
2. **调度器增加数据库级互斥与行锁**，使用调度器哨兵行和 `SELECT ... FOR UPDATE SKIP LOCKED`，降低多调度器实例重复领取任务的风险。
3. **任务日志实时性提升**，远端 `runner.py` 改为伪终端执行用户命令，并用 SSE 推送日志增量，前端可以更接近实时 tail 训练日志。
4. **环境安装链路进一步数据库化和 worker 化**，本机离线安装不再只是同步 API 请求，而是创建 `EnvPackage` / `EnvInstallJob`，由后台线程或 `env_install_worker` 执行。
5. **环境编译安装开始落地**，支持选择主节点或可见计算节点，支持默认/GPU/CPU 三种 GPU 可见性策略，worker 可通过 SSH 到计算节点执行编译安装。
6. **系统设置页增强**，设置项带描述、类型和选项，前端展示更友好，布尔和整数值会做归一化。
7. **远端脚本同步与部署自检脚本已经加入**，包括 `sync_remote_scripts.py` 和 `deployment_self_check.py`，为真实集群联调做准备。
8. **登录会话状态字段更清晰**，使用 `session_state/status_label/status_category`，避免前端把登录会话 offline 和节点掉线混淆。

因此，当前阶段判断为：

> **NebulaGrid 已经从“任务调度 MVP”继续推进到“真实集群联调与生产化加固阶段”。**

按照当前开发顺序，整体工程完成度可从上一版约 **80%–82%** 提升到约 **84%–86%**。

需要注意的是，虽然 Runtime Guard、环境安装 worker、调度器锁、日志 SSE 都已经开始实现，但仍需要真实集群验证，尤其是 SSH、NFS 路径、`nvidia-smi` 输出格式、GPU UUID 同步、远端脚本路径、conda activate、任务日志路径、编译安装路径一致性等问题。

### 本轮任务管理最重要进展

当前任务主链路已经从 MVP 继续推进为：

```text
用户提交任务
  ↓
Task / TaskRequirement / TaskDependency / TaskEvent 入库
  ↓
Scheduler 通过 DB 锁和 FOR UPDATE SKIP LOCKED 领取 wait 任务
  ↓
检查前驱依赖
  ↓
筛选用户可见且 online/scheduling_enabled 的节点
  ↓
按 GPU 数量、型号、复用策略、显存指标选择 GPU
  ↓
写 TaskAllocation / TaskRuntimeGuard
  ↓
任务状态 wait → dispatching
  ↓
Executor 扫描 dispatching
  ↓
SSH 调用远端 runner.py
  ↓
runner 用伪终端执行用户命令并实时写日志
  ↓
任务状态 dispatching → running
  ↓
Runtime Guard 采集 PID 树和 nvidia-smi GPU UUID
  ↓
发现 GPU 越权后标记 alloc_error 并终止进程组
  ↓
runner 写 status JSON
  ↓
Executor 回收 succeeded / failed / cancelled 状态
  ↓
释放 TaskAllocation
```

这已经明显超过上一版“调度执行 MVP”，开始进入运行安全和生产化阶段。

### 当前需要特别注意的问题

| 问题 | 影响 | 建议 |
|---|---|---|
| Runtime Guard 依赖 GPU UUID 同步 | 如果 monitor 未同步 GPU UUID，会进入 uuid_pending，不会判越权 | 部署前确保 monitor 正确写入 GPU UUID |
| Runtime Guard 需要真实越权场景测试 | 代码逻辑已实现，但需要实际验证误杀率和漏报率 | 用用户脚本刻意改 CUDA_VISIBLE_DEVICES 测试 |
| 调度器锁基于 Setting 哨兵行 | 可用，但仍建议真实 PostgreSQL 多实例压测 | 确认锁异常回滚和事务边界 |
| 远端 runner 使用伪终端 | 日志实时性更好，但可能影响某些程序判断终端行为 | 需要用 PyTorch、torchrun、普通 shell、长日志任务实测 |
| 取消运行中任务依赖轮询 | 不够实时 | 后续接事件通知或缩短 executor interval |

| 任务测试不足 | 调度执行链路风险高 | 补调度器、执行器、guard、日志 SSE 测试 |

### 阶段判断

任务管理已经进入 **生产化加固阶段**。  
当前已经具备真实调度、远端执行、日志、资源分配、Runtime Guard 基础能力。下一步重点是实测、测试覆盖、部署稳定性和异常恢复。

## 7. 当前最值得肯定的改进

### 7.1 Runtime Guard 已经真正开始工作

此前 Runtime Guard 只是记录 guard 表或扫描记录。  
当前已经实现：

- 根据 `root_pid` 远端采集 `ps` 进程表；
- 展开任务 PID 树；
- 查询 `nvidia-smi --query-compute-apps=pid,gpu_uuid,used_memory`；
- 找出该任务实际占用的 GPU UUID；
- 和调度器分配的 GPU UUID 做比对；
- 第一次越权写 warning；
- 连续确认越权后 kill 进程组；
- 任务状态置为 `alloc_error`；
- 释放 allocation；
- 写入任务事件和日志。

这正好对应此前“用户在代码里改 CUDA_VISIBLE_DEVICES 绕过调度”的核心风险。

### 7.2 调度器并发安全明显增强

调度器现在有两层保护：

1. 使用 `scheduler.instance_lock` 设置行作为事务哨兵；
2. 查询等待任务时使用 `FOR UPDATE SKIP LOCKED`。

这比单纯扫描 wait 任务安全很多，后续即便部署多实例也更不容易重复领取任务。

### 7.3 日志体验明显提升

远端 runner 改为伪终端执行用户命令，能够缓解 Python、训练框架和进度条缓冲导致日志不实时的问题。  
同时 API 增加 SSE 日志流，前端可以实时显示任务输出。

### 7.4 环境安装开始 worker 化

环境安装不再只是同步 API 请求。  
当前本机安装和已上传包安装都会进入 `EnvInstallJob`，worker 或后台线程执行，状态可查询，日志可读取。这为大包安装、编译安装、取消和恢复打下基础。

### 7.5 部署工具开始补齐

`sync_remote_scripts.py` 和 `deployment_self_check.py` 的加入很关键。  
真实集群问题往往不是业务逻辑，而是：

- 脚本没同步；
- SSH 不通；
- NFS 路径不一致；
- `nvidia-smi` 不可用；
- 远端没有 runner；
- UID/GID 或目录权限不一致。

现在已经有工具开始检查这些问题。

## 8. 当前主要风险

| 风险 | 所属阶段 | 影响 | 建议 |
|---|---|---|---|
| Runtime Guard 依赖 GPU UUID 同步 | 任务管理 | GPU UUID 缺失会进入 `uuid_pending`，无法判断越权 | 部署时必须确认 monitor 同步 GPU UUID |
| Runtime Guard 误杀/漏报未实测 | 任务管理 | 真实训练进程、torchrun、多进程场景复杂 | 用真实 PyTorch 多进程任务测试 |
| 调度器锁需要真实 PostgreSQL 验证 | 任务管理 | 异常回滚、多实例抢锁需要压测 | 增加多进程调度器测试 |
| runner 伪终端可能改变程序行为 | 任务管理 | 某些程序检测到 TTY 后输出格式改变 | 用常见训练脚本、torchrun、tqdm 实测 |
| SSE 可能被 Nginx 缓冲 | 任务管理 | 日志实时性失效 | Nginx 配置 `X-Accel-Buffering: no` 和禁缓冲 |
| 环境 compile 模式未充分实测 | 环境管理 | SSH、NFS、GPU 可见性、编译器路径都可能失败 | 在真实计算节点上跑 whl 编译测试 |
| EnvPackageManifest 未接入 | 环境管理 | 安装包无法精确追踪和回滚 | 安装成功后写 manifest |
| 文件/环境压缩炸弹检测不足 | 文件/环境管理 | 大压缩包可能占满磁盘或 inode | 限制总大小、文件数、层级 |
| Alembic 仍未引入 | 工程化 | 手写补列长期不可维护 | 尽快迁移到 Alembic |
| 自动化测试仍不足 | 全局 | 调度、执行、guard、worker 很难回归 | 补单元测试和集成测试 |
