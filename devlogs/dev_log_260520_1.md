## 1. 本次更新结论

本次新上传版本相比上一轮，最大的变化集中在 **文件管理模块**。

上一版中，文件管理的写操作大多还停留在“校验路径 + 返回 accepted”的占位状态；这一版已经推进为真实文件系统操作，并且前端也同步补齐了文件管理器交互。

当前文件管理已经支持：

- 文件列表；
- 文本/二进制预览；
- 图片、视频、音频预览；
- 单文件下载；
- multipart 文件上传；
- 新建目录；
- 新建文本文件；
- 保存文本文件；
- 复制文件或目录；
- 移动文件或目录；
- 重命名；
- 删除；
- 文件夹 zip 打包；
- zip 解压；
- 打包/解压任务进度展示；
- 页面刷新后读取最近一次文件任务状态；
- 路径边界校验；
- 解压路径穿越与软链接成员拦截；
- 文件操作审计调用。

这说明项目从“管理后台原型”进一步向“可用 Web 工作台”推进了一步。

不过，任务调度系统的核心 P0 问题仍然没有发生根本变化：

- `task_service.py` 仍然使用内存 `_TASKS`；
- `env_service.py` 仍然使用内存 `_ENVS/_PACKAGES/_JOBS`；
- `audit_service.py` 仍然使用内存 `_AUDIT_LOGS/_SETTINGS`；
- 调度器仍然只是扫描 DB 中的等待任务并打印数量；
- 执行器仍然只是扫描 `dispatching` 任务并打印数量；
- Runtime Guard 仍然只是扫描 guard 记录并打印数量；
- 环境安装 worker 仍然无法消费前端创建的内存安装作业；
- 任务日志仍然是占位文本。

因此，当前总体判断是：

> 文件管理模块有实质性推进；用户/认证/会话管理继续保持较高完成度；但 GPU 任务调度主链路仍未打通。

综合估算，当前工程完成度从上一轮约 **47%** 提升到约 **51%**。  
提升主要来自文件管理模块，而不是调度执行主链路。

## 5. 本次最值得肯定的地方

### 5.1 文件管理从占位进入可用阶段

这是本轮最大进展。文件管理现在已经不是简单的路径校验接口，而是具备了完整的 Web 文件管理器雏形：用户可以维护自己的项目目录，上传训练脚本和配置文件，在浏览器中编辑文本，下载结果文件，对目录进行 zip 打包，并把 zip 解压到目标目录。

这对 NebulaGrid 的 B/S 化很重要，因为系统的目标之一就是减少用户 SSH 到主节点的需求。

### 5.2 文件路径安全意识明显增强

本轮加入了多处安全边界：虚拟根 `/` 映射到用户 home；普通用户路径被限制在自己的 user root；管理员路径默认映射到主账户目录；删除和移动会保护根目录；zip 解压前检查绝对路径和 `..`；zip 解压前拒绝软链接成员；复制/移动目录时拒绝目标位于源目录内部；上传文件名会丢弃浏览器传来的路径片段。

### 5.3 前端交互明显完善

文件页面已经补齐文件操作按钮区、上传表单、文本编辑器、图片/音视频预览、文件目标目录选择弹窗、打包/解压进度条和自动刷新文件任务状态。前端文件管理器已经可以进入实际试用阶段。

## 6. 当前仍然存在的关键问题

### 6.1 任务主链路仍未解决

当前 `task_service.py` 仍然使用 `_TASKS` 内存列表，调度器扫描的是数据库 `Task` 表。这仍然意味着：用户提交任务后不会进入数据库；调度器看不到这些任务；执行器不会启动它们；Runtime Guard 无法监管；服务重启后任务丢失；dashboard 的任务统计仍不可靠。

### 6.2 环境管理链路仍未解决

当前 `env_service.py` 仍然使用 `_ENVS/_PACKAGES/_JOBS`。因此环境登记不会进入 `envs` 表，环境包不会进入 `env_packages` 表，安装作业不会进入 `env_install_jobs` 表，`env_install_worker.py` 扫数据库但前端创建的是内存 job。

### 6.3 审计和设置仍未落库

文件操作现在大量调用 `record_audit()`，但 `record_audit()` 本身仍然写入内存 `_AUDIT_LOGS`。服务重启后，文件删除、移动、解压等危险操作的审计记录会丢失。管理员后台设置也仍写 `_SETTINGS`，worker 仍从数据库 `settings` 表读取，二者可能不一致。

### 6.4 文件任务状态仍是内存

`_FILE_JOBS` 是本轮新增的内存状态，用于记录每个用户最近一次打包/解压任务。短期可满足单进程开发环境，但生产环境存在风险：API 进程重启后任务状态丢失；多进程部署时不同 worker 之间无法共享状态；无法做历史追踪；无法限制全局并发。

### 6.5 zip/tar 支持不完全一致

`extract_archive()` 函数中存在 zip/tar/tar.gz/tar.bz2/tar.xz 的安全解压逻辑，但当前 API 的 `start_extract_job()` 主要限制为 `.zip`，前端也显示“解压 zip 文件”。因此当前实际对用户开放的解压能力主要是 zip。如果文档继续宣称支持 tar/tar.gz，需要补 API 和前端；如果近期只支持 zip，文档应同步收敛描述。

## 10. 对当前版本的评价

当前版本可以概括为：

> 文件管理模块进入可用阶段，Web 工作台能力明显增强；但 NebulaGrid 的 GPU 调度核心仍处于占位状态。

判断 MVP 是否成立的标准仍然是：

1. 用户提交任务后，任务进入数据库；

目前文件管理已经向 MVP 靠近，但调度系统 MVP 尚未成立。
