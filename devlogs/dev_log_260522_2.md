## 1. 本次更新结论

本次检查以新上传的 `NebulaGrid0522_2.zip` 为准。  
和上一轮 `NebulaGrid-0522.zip` 相比，这一版的核心变化非常明显：

> **任务管理已经正式进入主开发阶段。**

上一版中，任务管理仍主要停留在接口和模型预备阶段；这一版已经完成了几项关键突破：

1. `_TASKS` 内存任务列表已经被移除；
2. 任务创建、查询、编辑、取消、删除、重提、批量提交已经接入数据库；
3. `Task`、`TaskRequirement`、`TaskDependency`、`TaskEvent`、`TaskAllocation`、`TaskRuntimeGuard` 开始被服务层、调度器、执行器实际使用；
4. 调度器不再只是打印等待任务数量，而是会扫描 `wait` 任务、判断依赖、筛选可见节点、选择 GPU、写入 allocation，并把任务推进到 `dispatching`；
5. 执行器不再只是打印 `dispatching` 任务数量，而是会通过 SSH 调用远端 `runner.py`，启动任务、写入 PID/PGID、记录日志路径，并把任务推进到 `running`；
6. 远端 runner 已经能生成 wrapper 脚本，在计算节点后台执行用户命令，并将返回码写入状态文件；
7. 执行器可以读取远端状态文件，回收任务、释放 allocation，并把任务置为 `succeeded` 或 `failed`；
8. 任务日志接口已经读取真实日志文件尾部，而不是返回占位文本；
9. 前端任务管理已经从原来的基础展示升级为等待区、执行区、历史区三分区，支持添加、批量添加、修改、挂起、删除、中止、重提、查看日志、选择前驱、选择节点、选择 GPU 型号、选择工作目录等操作。

因此，当前阶段判断为：

> **节点管理、用户管理、文件管理和环境管理已经基本支撑后续任务运行；任务管理也已经从“占位阶段”进入“调度执行 MVP 阶段”。**

按照当前开发顺序，整体工程完成度可从上一轮约 **73%–75%** 提升到约 **80%–82%**。

不过需要注意：当前任务管理虽然已打通 MVP 主链路，但仍不是完整生产版调度系统。主要缺口包括：

- Runtime Guard 仍然只是扫描 guard 记录，没有真正检测 PID/GPU 越权；
- 调度器没有显式数据库行锁，多调度器实例下可能存在重复领取风险；
- 远端 runner 脚本同步、systemd worker 部署、SSH 凭据、NFS 路径一致性仍需真实集群验证；
- 运行中任务取消只通过 executor 下一轮回收远端进程，实时性依赖 worker 轮询；
- `EnvPackage / EnvInstallJob` 异步环境安装链路仍未完全打通；
- 任务自动化测试还需要补齐。

## 2. 本次主要新增或变化内容

|---|---|---|---|
| 任务持久化 | 任务仍在 `_TASKS` 内存中 | `_TASKS` 已移除，任务服务接入 `Task` 等数据库表 | 任务重启不丢失，调度器能看到前端提交的任务 |

| 前驱依赖 | 仅模型预备 | `TaskDependency` 被接入，调度器检查前驱是否成功 | 支持任务之间的简单依赖 |

| 任务删除 | 基础或缺失 | 支持删除前预览后继任务，可递归删除后继 | 删除关系更安全 |
| 任务重提 | 基础或缺失 | 支持基于历史任务重新生成新任务 ID | 便于实验复跑 |
| 任务日志 | 占位文本 | 读取真实日志文件尾部，支持 tail 参数 | 前端可查看实际执行日志 |
| 调度器 | 只扫描 DB 并打印数量 | 实现等待任务排序、依赖检查、节点筛选、GPU 选择、allocation 写入 | 调度器进入 MVP 可用阶段 |
| GPU 分配 | 表已定义但未写入 | 写入 `TaskAllocation`，支持 exclusive/reuse/cpu 模式 | 节点 GPU 占用展示和后续 guard 有数据基础 |
| GPU 复用 | 无实质逻辑 | 支持 `allow_gpu_reuse`、`max_reuse_count`、显存比例判断 | 具备基础复用策略 |
| GPU 型号筛选 | 无实质逻辑 | 调度器可根据 `gpu_types` 匹配 GPU 型号 | 用户可指定 GPU 类型 |
| 指定节点 | 节点字段存在 | 任务 requirement 可指定 node_id，并校验用户可见性 | 用户不能伪造私有节点 |
| 执行器 | 只扫描 dispatching | SSH 调用远端 runner，记录 PID、PGID、状态文件和日志路径 | 任务可真正被远端启动 |
| 远端 runner | 骨架 | 生成 wrapper，后台执行命令，写状态 JSON | 支持计算节点运行任务 |
| 任务完成回收 | 无 | 执行器读取远端 status 文件，写 succeeded/failed，释放 allocation | 任务生命周期闭环初步形成 |
| 任务取消 | 主要内存状态 | DB 状态改 cancelled；运行中任务由 executor kill 远端进程组 | 运行中取消进入 worker 回收路径 |
| 任务守护记录 | 表存在 | 调度器/执行器创建并更新 `TaskRuntimeGuard` 的 PID/PGID/状态 | 为 Runtime Guard 后续检测做准备 |
| 前端任务页 | 基础列表 | 新增等待区/执行区/历史区、任务操作栏、表单抽屉、路径选择、节点/GPU/前驱选择 | 任务管理前端进入可用阶段 |
| Dashboard | 任务统计依赖任务服务 | 任务统计开始读取数据库任务服务 | 首页统计不再依赖内存任务列表 |
| Runtime Guard | 占位 | 仍未实现 GPU 越权检测 | 后续任务阶段重点补齐 |
| 环境安装 worker | 未打通 | 仍未完全打通 | 环境异步安装链路仍需收尾 |

### 任务主链路当前状态

当前已经具备如下 MVP 链路：

```text
用户提交任务
  ↓
Task / TaskRequirement / TaskEvent 入库
  ↓
Scheduler 扫描 wait 任务
  ↓
检查前驱依赖
  ↓
筛选用户可见且 online/scheduling_enabled 的节点
  ↓
按 GPU 数量、型号、复用策略、显存指标选择 GPU
  ↓
写 TaskAllocation / TaskRuntimeGuard
  ↓
任务状态 wait → dispatching
  ↓
Executor 扫描 dispatching
  ↓
SSH 调用远端 runner.py
  ↓
runner 在计算节点后台运行 wrapper
  ↓
任务状态 dispatching → running
  ↓
runner 写日志和 status JSON
  ↓
Executor 读取 status
  ↓
任务状态 running → succeeded / failed
  ↓
释放 TaskAllocation
```

这说明任务管理已经迈过最关键的“前端任务服务写内存、调度器看不到任务”的旧问题。

### 当前需要特别注意的问题

| 问题 | 影响 | 建议 |
|---|---|---|
| Runtime Guard 仍未真正检测 GPU 越权 | 用户仍可能在代码中修改 CUDA_VISIBLE_DEVICES | 实现 PID 树 + nvidia-smi 查询 + GPU UUID 比对 |
| 调度器没有显式行锁 | 多个 scheduler 实例可能重复领取任务 | 使用 `SELECT FOR UPDATE SKIP LOCKED` 或保证 systemd 单实例 |
| Executor 依赖 SSH/NFS/远端脚本路径 | 真实集群部署中易因路径不一致失败 | 补远端脚本同步工具和部署自检 |
| runner 使用 shell wrapper 执行用户命令 | 需关注命令注入边界和日志路径安全 | 目前命令来自用户任务本身，仍需限制执行上下文 |
| 取消运行中任务依赖轮询 | 不够实时 | 可后续接事件通知或缩短 executor 间隔 |
| CPU-only 任务目前仍分配一个节点 | 合理但需前端解释 | 可在任务表中标明 CPU 模式 |
| 日志接口只读 tail 文本 | 可用但不够实时 | 后续支持 SSE/WebSocket tail |
| 任务测试不足 | 调度执行链路风险高 | 补数据库任务、调度、执行器、依赖、日志测试 |

### 阶段判断

任务管理已经进入 **主开发阶段**，并且已经达到 **MVP 初步打通** 的状态。  
下一步重点应该是：

1. Runtime Guard；
2. 调度/执行真实集群联调；

## 7. 当前最值得肯定的改进

### 7.1 任务不再是内存状态

这是本轮最大进展。  
此前任务 API 写内存，而调度器扫数据库，导致任务主链路天然断裂。现在任务已经写入数据库，调度器可以真正消费前端提交的任务。

### 7.2 调度器开始真正分配资源

当前调度器已经不是占位：

- 扫描 wait 任务；
- 按紧急程度和优先级排序；
- 检查前驱任务；
- 过滤用户可见节点；
- 过滤在线且允许调度的节点；
- 匹配 GPU 数量和型号；
- 检查 GPU 占用和复用策略；
- 写入 allocation；
- 将任务推进到 dispatching。

这说明任务调度主链路已经形成。

### 7.3 执行器开始真正启动远端任务

当前执行器已经能通过 SSH 调用远端 runner，runner 会在计算节点写 wrapper 并后台执行用户命令。  
这意味着系统从“提交任务”推进到了“尝试运行任务”。

### 7.4 任务日志开始真实可读

日志接口不再返回占位文本，而是读取日志文件尾部。  
虽然还不是实时流式日志，但已经具备基本查看能力。

### 7.5 前端任务管理进入可用阶段

前端已经具备任务管理核心交互：

- 等待区；
- 执行区；
- 历史区；
- 添加任务；
- 批量添加；
- 修改任务；
- 挂起任务；
- 删除任务；
- 中止任务；
- 重新提交；
- 查看日志；
- 选择环境；
- 选择工作目录；
- 选择节点；
- 选择 GPU 型号；
- 选择前驱任务。

这已经接近用户实际使用任务系统的基本需求。

## 8. 当前主要风险

| 风险 | 所属阶段 | 影响 | 建议 |
|---|---|---|---|
| Runtime Guard 未真正检测 | 任务管理 | 用户仍可能越权使用 GPU | 实现 PID 树、nvidia-smi 查询和 GPU UUID 比对 |
| 调度器没有行锁 | 任务管理 | 多实例调度器可能重复领取任务 | 使用 `SELECT FOR UPDATE SKIP LOCKED` 或强制单实例 |
| SSH/runner/NFS 未充分联调 | 任务管理 | 真实计算节点路径不一致会导致启动失败 | 增加部署自检和远端脚本同步 |
| 取消运行中任务依赖轮询 | 任务管理 | 中止不够实时 | 后续接事件或缩短 executor interval |
| 任务日志不是实时流 | 任务管理 | 用户需要手动刷新 | 后续实现 SSE/WebSocket tail |
| EnvInstallJob 队列未打通 | 环境管理 | 环境安装和任务执行 worker 体系不统一 | 尽快将环境安装也迁移到 DB job + worker |
| 本机环境安装是同步请求 | 环境管理 | 大包安装占用 API 请求 | 改成 EnvInstallJob + worker |
| 节点错误码仍有 500 问题 | 节点管理 | 前端提示不友好 | 改为 400/422 |
| 压缩炸弹检测不足 | 文件/环境管理 | 导入大压缩包可能占满磁盘 | 限制总大小、文件数量、层级 |
| 自动化测试不足 | 全局 | 调度执行链路难以回归 | 补调度器、执行器、任务 CRUD、依赖测试 |
