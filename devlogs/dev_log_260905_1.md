## 2. 三个月试运行后的主要问题类型

从当前提交、测试用例、文档改动和代码结构反推，试运行期间遇到的问题主要集中在以下几类。

### 2.1 任务停止与远端进程回收

这是本阶段最重要、也是改动最大的 Bug 类型。

旧流程中潜在问题包括：

- 用户点击“停止”后，数据库可能已经认为任务结束，但远端进程仍未真正退出；
- SSH 超时可能被错误理解为“进程已经停止”；
- allocation 可能被过早释放，导致新的任务重新使用同一张 GPU，而旧进程还在运行；
- 任务自然结束与用户点击停止同时发生时存在状态竞争；
- 旧 runtime/status 文件可能污染重新提交后的新任务；
- PID 被 Linux 复用后，有误杀其他进程的风险；
- 节点重启后原 PID 可能失去身份可信度；
- executor 启动远端任务时 SSH 超时，但实际上 runner 可能已经把用户进程启动起来。

当前版本针对这些问题做了较大规模的协议级修复。

### 2.2 节点监控偶发离线或 SSH 频繁建立

原节点监控偏向短连接轮询。长期试运行后，这种模式容易出现：

- 每个周期重新建立 SSH；
- 网络短暂抖动时节点状态反复变化；
- SSH 进程开销和日志噪声较大；
- SSH 连接没有断，但远端 monitor 不再输出时无法及时发现；
- 节点断线后缺少明确的自动重连生命周期。

当前版本将其改为每节点独立 SSH 长连接。

### 2.3 PyTorch 与不同年代 GPU 的兼容性

实验室 GPU 通常不是单一型号。当前项目本身就有 RTX 40 系、RTX 30 系、Tesla P40 等不同年代 GPU。

真实用户使用中，环境中的 PyTorch 版本可能：

- 原生支持某张 GPU；
- 只带同一主版本的较低 SM cubin；
- 完全不支持某张老卡或新卡；
- `torch.cuda.is_available()` 在某台卡上理论可用，但二进制实际不包含对应架构。

因此单纯按“节点在线 + GPU 空闲”调度并不足够。

当前版本新增了 PyTorch 架构与 GPU Compute Capability 联动。

### 2.4 文件上传后脚本无法执行

用户通过 SSH、Samba 或 Web 上传 `.sh` / 可执行脚本后，文件执行位可能不符合任务运行主账户的要求，导致：

```text
Permission denied
```

当前文件管理页新增文件权限显示和“授予执行权限”操作。

### 2.5 任务列表和页面刷新体验

试运行后任务数量逐渐增加，旧实现容易出现：

- 等待区、执行区、历史区切换时页面闪空；
- SSE 任意任务变化都会触发整个任务页重新加载；
- 任务列表构建存在 N+1 查询；
- 已修改等待任务仍显示旧 allocation 的节点/GPU，让用户误以为保存失败；
- 任务表单打开时等待前驱任务加载，操作体验不流畅。

当前已通过数据库索引、批量加载、分区 cursor 和前端缓存进行优化。

### 2.6 文件预览体验

用户提出的界面体验问题主要集中在文件管理：

- 选中文件后右侧反馈不够立即；
- 长文件名不容易确认当前选中了什么；
- 大文本只显示一小段但没有方便的完整查看入口；
- 不支持预览的压缩包/二进制文件仍可能被无意义读取；
- 视频以 Base64 截断预览，长视频无法正常拖动进度；
- 原生浏览器视频控件与系统整体 UI 风格不一致。

9 月 5 日版本对此进行了集中重构。

## 3. 本轮最重要的 Bug 修复

## 3.1 任务停止流程改为“两阶段停止”

旧逻辑中最危险的问题是：

> **“停止请求已经发出”不等于“远端进程已经停止”。**

当前任务停止生命周期调整为：

```text
running
  ↓ 用户点击停止
cancelling
  ↓
保留 TaskAllocation
  ↓
写 cancel 控制文件 / 查询返回码 / TERM / KILL
  ↓
验证同一次 launch 的远端进程组已真正退出
  ↓
cancelled
  ↓
释放 allocation
```

如果平台无法确认远端进程已经结束，则：

```text
cancelling
  ↓ 超过 NEBULAGRID_CANCELLING_TIMEOUT_SECONDS
unknown
  ↓
释放 allocation
  ↓
管理员必须人工核查节点是否仍有孤儿进程
```

这是一个非常重要的语义修正：

| 状态 | 当前含义 |
|---|---|
| `starting` | runner 正在建立本次启动记录 |
| `running` | 本次 launch 已确认运行 |
| `cancelling` | 停止意图已写入，但远端退出尚未确认，allocation 仍保留 |
| `cancelled` | 同一次 launch 已确认退出 |
| `offline_error` | 远端执行异常，且潜在进程已完成安全回收 |
| `alloc_error` | Runtime Guard 确认 GPU 越权并完成停止 |
| `unknown` | 超过停止确认时限，平台无法证明远端已停止 |

这使“数据库状态”和“真实远端进程状态”的关系比之前严谨很多。

---

## 3.2 引入 launch_id，防止旧状态文件污染新任务

当前每次任务实际被调度时，使用 `TaskAllocation.id` 作为本次运行的：

```text
launch_id
```

远端 runtime/status/cancel 文件都必须和当前 allocation 对应。

这解决了如下问题：

```text
任务 A 第一次运行
allocation = 101
生成旧 status 文件

用户重新提交 / 再次调度
allocation = 205

如果仍读取旧 status：
可能把第二次任务误判为第一次任务的结果
```

现在控制文件必须满足：

```text
payload.launch_id == 当前 TaskAllocation.id
```

否则不会用于结束、停止或判断当前任务。

---

## 3.3 PID + PGID + process_start_time + boot_id 四重身份校验

单纯用 PID 终止任务不够安全，因为 Linux 会复用 PID。

当前 runner 在启动后记录：

- PID；
- PGID；
- `/proc/<pid>/stat` 中的进程启动时钟；
- `/proc/sys/kernel/random/boot_id`；
- launch_id。

Runtime Guard 和 executor 在终止进程前重新校验这些信息。

目的如下：

| 校验项 | 防止的问题 |
|---|---|
| launch_id | 旧任务控制文件污染新任务 |
| PID | 找到目标进程 |
| PGID | 回收任务整个进程组 |
| process_start_time | PID 被其他进程复用 |
| boot_id | 节点重启后旧 PID 身份失效 |

相比 5 月版本，这是任务执行协议上的一次明显升级。

---

## 3.4 SSH 超时不再直接视为任务失败或停止成功

当前将远端任务相关超时拆成三个概念：

| 配置 | 默认值 | 作用 |
|---|---:|---|
| `NEBULAGRID_SSH_CONNECT_TIMEOUT_SECONDS` | 20s | SSH TCP 建连、握手、认证 |
| `NEBULAGRID_TASK_START_TIMEOUT_SECONDS` | 120s | 等待 runner 写出本次启动回执 |
| `NEBULAGRID_SSH_OPERATION_TIMEOUT_SECONDS` | 30s | 状态查询、停止、退出确认等短操作 |

这是非常符合实际集群环境的调整。

例如：

- SSH 连接可能 2 秒就成功；
- NFS 上 Python 环境冷启动可能需要 30 秒；
- conda 激活可能较慢；
- runner 已经启动任务，但主节点没有及时收到回执。

现在不会把这些情况混为同一个“SSH 超时”。

---

## 3.5 明确 return_code 优先级

当前远端 status 中如果存在明确的：

```text
return_code
```

则直接按程序返回值结束任务：

```text
0     → succeeded
非 0  → failed
```

不会因为用户此前发过停止请求就强行覆盖任务真实退出结果。

这解决了：

> “任务恰好自然结束，同时用户点击停止”

这种典型竞态。

---

## 3.6 Runtime Guard 与 executor 职责重新分离

Runtime Guard 现在主要负责：

1. 验证本次 launch 身份；
2. 展开任务 PID 树；
3. 查询 `nvidia-smi compute-apps`；
4. 找到实际使用的 GPU UUID；
5. 与 TaskAllocation 比对；
6. 连续确认越权；
7. 把任务置为停止中。

真正：

- TERM；
- KILL；
- 检查进程是否消失；
- 释放 allocation；
- 写最终 `alloc_error`

主要由 executor 完成。

这个分工比“Guard 发现问题立即释放资源”更稳妥。

---

## 3.7 强制下线节点不再立即假定任务已停止

管理员强制下线节点时，当前流程也采用两阶段思想：

1. 先把节点标记为 offline；
2. 关闭 scheduling；
3. 相关任务进入 cancelling；
4. 提交事务；
5. 再由 executor 发停止信号；
6. 确认退出后才释放 allocation。

这避免长 SSH 操作占着数据库事务，也避免节点下线过程中资源提前被其他任务重新分配。

## 4. 节点监控架构升级

## 4.1 从周期 SSH 短连接改为每节点 SSH 长连接

6 月 28 日以后，节点监控架构已经明显变化。

当前主节点为每个计算节点维护一个：

```text
NodeMonitorWorker
```

每个 worker 保持一条 SSH 长连接，并在计算节点运行：

```bash
monitor.py --loop --interval <seconds>
```

计算节点持续输出 JSON Lines。

相比旧版：

```text
master
  每 5 秒
    ssh node
      python monitor.py
    退出 ssh
```

现在变为：

```text
master
  ├─ node-a SSH long connection
  │    ├─ JSON snapshot
  │    ├─ JSON snapshot
  │    └─ ...
  │
  ├─ node-b SSH long connection
  └─ node-c SSH long connection
```

优点包括：

- 降低频繁 SSH 握手开销；
- 网络状态变化更容易识别；
- 节点状态更新更连续；
- 更适合几十台以内的实验室节点规模。

---

## 4.2 Watchdog 检测“连接存在但无数据”

新增：

```text
monitor.watchdog_timeout_seconds
```

默认约 600 秒。

它解决的不是 SSH 断开，而是：

> SSH 子进程还活着，但远端 `monitor.py` 已经卡住或长时间没有输出有效 JSON。

超过 watchdog 后：

1. 节点标记 offline；
2. 主动关闭该 SSH；
3. 进入自动重连流程。

---

## 4.3 自动重连次数可配置

新增：

```text
monitor.reconnect_attempts
```

默认 3 次。

监控流程现在为：

```text
online
  ↓ SSH断开 / watchdog
offline
  ↓
reconnecting
  ↓ 成功
online

或

reconnecting
  ↓ 次数耗尽
offline
  ↓
等待管理员手动“重连”
```

每次重连尝试以及重连耗尽都会写入审计日志。

---

## 4.4 管理员强制下线不会被 monitor 自动拉回

当前：

```text
manual_offline
```

或者：

```text
offline + scheduling_enabled = false
```

的节点不会自动建立 monitor SSH。

必须管理员显式点击：

```text
重连
```

之后才重新纳入监控目标。

这修复了“管理员刚强制下线，下一轮 monitor 又把它标 online”的语义冲突。

## 5. GPU / PyTorch 兼容性支持

这是 9 月初新增的重要能力。

## 5.1 环境记录 PyTorch 二进制支持架构

环境检测现在会调用：

```python
torch.cuda.get_arch_list()
```

并保存：

- `pytorch_version`
- `pytorch_cuda_version`
- `pytorch_arch_list`

例如：

```text
PyTorch 2.x
CUDA 12.x
sm_70
sm_75
sm_80
sm_86
```

环境安装、升级或删除 PyTorch 后会自动重新探测。

---

## 5.2 GPU 记录 Compute Capability

节点 monitor 额外执行：

```bash
nvidia-smi --query-gpu=index,compute_cap --format=csv,noheader,nounits
```

将 GPU Compute Capability 写入数据库。

如果旧驱动不支持 `compute_cap` 查询：

- 不影响基本 GPU 清单；
- 保留上一次有效值；
- 管理员可按 GPU index 手动覆盖。

---

## 5.3 新增兼容性分类

当前系统将 PyTorch 与 GPU 组合分类为：

| 状态 | 含义 |
|---|---|
| `native_supported` | PyTorch 二进制存在精确 `sm_xx` |
| `same_major_compatible` | 同一 major 内存在更低 minor 的普通 cubin |
| `unsupported` | 没有可用 SM cubin |
| `unknown` | 缺少 PyTorch 或 Compute Capability 信息 |

值得注意的是：

> **`compute_xx` PTX 不参与产品层兼容判断。**

这是一个偏保守但合理的策略，可以避免因为理论上可以 JIT 而把实际上可能跑不起来的组合显示为“支持”。

带 `a`、`f` 等专用 SM 后缀也不会简单按同主版本向上兼容。

---

## 5.4 调度器开始使用兼容性

当用户 **没有显式指定 GPU 型号** 时：

- 原生支持 → 正常参与调度；
- 同主版本兼容 → 正常参与调度；
- unknown → 正常参与调度；
- unsupported → 被过滤。

如果用户 **显式勾选 GPU 型号**：

> 视为用户强制选择。

此时调度器不会因为兼容性判定为红色而擅自修改用户选择。

这个设计比较符合科研环境：

- 默认帮助用户避坑；
- 专业用户仍然保留强制控制权。

## 6. 文件管理 Bug 修复与界面优化

## 6.1 用户上传脚本后可直接授予执行权限

文件预览现在展示：

- mode；
- owner executable；
- group executable；
- other executable；
- 平台主账户是否可执行。

并提供：

```text
授予执行权限
```

后端会：

1. 给文件 owner 补 `x`；
2. 如果系统支持 POSIX ACL，则给 `NEBULAGRID_MAIN_LINUX_USER` 补 `rwx` ACL；
3. 写入文件审计。

这个功能直接解决用户上传 `.sh` 后任务报：

```text
Permission denied
```

的问题。

---

## 6.2 文件预览不再无意义读取任意二进制文件

旧预览逻辑会对二进制文件读取前 2 MiB，再 Base64 返回。

当前只对真正支持渲染的：

- image；
- audio；
- video

做媒体预览。

对于：

- `.zip`
- `.tar`
- 模型文件
- 其他未知二进制

只返回：

- 文件名；
- MIME；
- 文件大小；
- “不支持在线预览”。

**不会读取文件内容。**

对于实验室场景中的大模型权重、数据压缩包，这会明显减少无意义磁盘 IO。

## 6.3 文本默认预览上限调整到 2 MiB

文本文件现在：

```text
<= 2 MiB
    可在线编辑和保存

> 2 MiB
    默认只读取前 2 MiB
    显示“加载完整文件”
```

用户可以主动：

```text
加载完整文件
```

但超 2 MiB 的完整文本进入：

```text
只读
```

状态，避免用户误把截断内容保存回原文件导致文件被破坏。

## 6.4 修复“大文件预览实际仍全量读入内存”

当前新增：

```python
read_file_prefix()
```

通过：

```python
file.read(limit)
```

读取文件前缀。

避免：

```python
path.read_bytes()[:limit]
```

这种表面只取前 2 MiB、实际上已经把整个文件加载进内存的写法。

这是一个实质性后端性能修复。

## 6.5 视频预览改为 Range Streaming

旧视频预览依赖：

```text

```

对于较大视频会被预览限制截断，导致只能播放开头。

当前新增：

```text
GET /api/files/media
```

支持 HTTP：

```text
Range: bytes=...
```

返回：

```text
206 Partial Content
Content-Range
Accept-Ranges: bytes
```

浏览器可以：

- 拖动进度；
- 跳播；
- 按需读取文件；
- 不把整个视频加载进 API 内存。

对于用户希望直接在文件管理页面查看实验视频、结果视频的需求，这是明显升级。

只有运行中和历史任务才展示真实 allocation。

## 13. 当前需要重点关注的新风险

结合三个月试运行结果，之前的：

- 压缩炸弹；
- Web 超大文件；
- 环境包精细审计；

仍然属于低优先级。

当前真正值得关注的风险已经发生变化。

### 13.1 升级时主节点和 runner 版本必须一致

9 月 4 日以后，executor / runner 使用新的：

- launch_id；
- process_start_time；
- boot_id；
- cancel/status/runtime 文件协议。

因此：

> **不能在仍有旧任务运行时直接滚动更新一半组件。**

升级前应：

1. 停止 scheduler；
2. 等待 starting/running/cancelling 任务清空；
3. 停止 API / monitor / executor / guard / env worker；
4. 更新主节点代码；
5. 安装依赖；
6. 同步 remote scripts；
7. 再统一启动服务。

这是当前最重要的运维规则之一。

---

### 13.2 `unknown` 任务必须人工核查

`unknown` 不等于：

```text
远端已经停止
```

它只表示：

```text
平台等待停止确认超时
→ 为防止永久占用调度资源而归档
→ 但无法证明远端进程不存在
```

因此管理员看到 `unknown` 后：

- 不应直接认为安全；
- 应先检查 `ps` / `nvidia-smi`；
- 再决定是否重新提交。

---

### 13.3 Runtime Guard 当前仍是进程组级保护

当前 runner 使用：

```text
start_new_session=True
```

创建独立进程组。

如果用户程序主动：

```text
setsid
double fork
```

脱离 runner 进程组，现有机制不保证完整回收。

实验室可信用户环境下问题不大。

如果未来需要防御真正不可信 workload，应考虑：

- systemd scope；
- cgroup；
- 独立 UID；
- 容器。

当前不属于上线阻塞项。

---

### 13.4 PyTorch 兼容性数据可能因环境未检测而 unknown

旧环境升级后，如果没有重新执行环境检测：

```text
pytorch_arch_list
```

可能为空。

结果会显示：

```text
unknown
```

调度器不会因此过滤 GPU，但用户看不到兼容性提示。

建议升级后对长期使用环境统一跑一遍“检测”。

| 任务刚开始就停止 | starting/cancel race |
| 任务自然结束瞬间停止 | return_code race |
| 节点 SSH 临时断开后停止 | cancelling 重试 |
| 节点彻底断电后停止 | unknown |
| 重复点击停止 | 幂等 |
| stop 后立即重提 | 确认系统是否阻止危险操作 |
| 任务 A 旧 status + 任务 A 重提 | launch_id |
| 节点重启后旧 PID | boot_id |
| torchrun 多子进程 | PGID/PID tree |
| Runtime Guard 越权 | alloc_error |

如果这一轮全部稳定，任务子系统可以认为进入成熟期。

## 16. 最新总体判断

截至 **2026-09-05**，NebulaGrid 已经经历：

```text
5 月中旬：主体功能开发
       ↓
5 月下旬：实机部署和首轮联调
       ↓
6 月：节点监控长期运行优化
       ↓
7–8 月：真实实验室试运行
       ↓
9 月初：用户反馈驱动集中修复和 UI 优化
```

当前模块完成度：

| 模块 | 当前完成度 |
|---|---:|
| 节点管理 | **94%–96%** |
| 用户管理 | **92%–94%** |
| 文件管理 | **92%–94%** |
| 环境管理 | **90%–92%** |

总体功能完成度：

> **约 95%–96%**

试运行稳定性：

> **约 92%–94%**

当前最重要的变化已经不是新增多少页面，而是：

1. **任务停止不再提前释放 GPU；**
2. **远端任务具备 launch 身份，旧状态文件不能污染新任务；**
3. **PID 复用和节点重启导致误杀的风险被显著降低；**
4. **节点监控改为 SSH 长连接，并具备 watchdog 与自动重连；**
5. **PyTorch 环境和 GPU Compute Capability 开始参与调度兼容判断；**
6. **用户上传脚本后可以在 Web 中修复执行权限；**
7. **任务列表在长期积累数据后进行了索引、批量查询和前端缓存优化；**
8. **文件页面针对真实用户反馈完成了大文本、二进制文件和视频预览重构。**

因此，目前 NebulaGrid 可以认为已经从：

> **“课题组内部试运行系统”**

逐渐进入：

> **“课题组长期使用、持续维护和小版本迭代系统”**

阶段。

下一阶段不建议再进行大规模功能扩张，而应围绕：

> **任务生命周期回归测试 → monitor 长稳 → GPU 兼容 metadata 回填 → 小步 UI 优化 → CI → 运维版本管理**

持续收口。
