## 2. 总体结论

当前 NebulaGrid 3.0 已经从纯项目骨架进入 **“前后端原型 + 部分数据库固化 + 多个核心 worker 占位”** 阶段。

其中，用户管理、登录管理、导师学生关系、节点登记、前端管理页面等管理面功能已经具备较高完成度；但是，作为 GPU 任务调度系统的核心链路，即：

- 任务入库；
- 调度器分配 GPU；
- 执行器远端启动任务；
- Runtime Guard 检查 PID / GPU 使用情况；
- 任务日志读取；
- 任务状态恢复；

目前仍没有完全打通。

因此，当前系统更接近一个 **管理后台原型 + 数据模型雏形 + 调度执行占位框架**，距离完整可运行的 B/S 架构 GPU 调度系统仍需要继续补齐任务、环境、审计、设置等核心链路。

综合估算，当前工程完成度约为 **45%**。

## 5. 当前核心风险

### 5.1 任务主链路尚未打通

当前前端可以提交任务，后端也可以返回任务列表，但任务服务写入的是内存 `_TASKS`。与此同时，调度器扫描的是 PostgreSQL 中的 `Task` 表。

这意味着：

- 前端提交的任务不会进入数据库；
- 调度器看不到这些任务；
- 执行器无法启动这些任务；
- Runtime Guard 也无法对这些任务进行监管；
- 服务重启后任务全部丢失。

这是当前系统最关键的 P0 问题。

### 5.2 环境管理链路脱节

环境登记、包登记、安装作业目前主要在 `env_service.py` 的内存变量中维护；但是 `env_install_worker.py` 扫描的是数据库中的 `EnvInstallJob`。

因此当前环境包安装链路也存在类似问题：

- 前端创建的安装作业不会被 worker 消费；
- whl / 源码包上传尚未真正实现；
- 编译模式、指定节点/GPU 编译、环境锁等功能仍未落地。

### 5.3 管理员设置与 worker 读取来源不一致

初始化脚本会向 `settings` 表写入默认设置，调度器也会从数据库读取部分设置；但管理员后台修改设置时，当前服务层实际写入的是内存 `_SETTINGS`。

这会导致：

- 管理员页面显示设置已修改；
- worker 仍然读取数据库旧值；
- 重启后管理员设置丢失。

### 5.4 审计日志无法长期追溯

审计服务虽然已经有 `AuditLog` ORM 模型，但实际写入的是内存 `_AUDIT_LOGS`。这会导致：

- 服务重启后审计记录丢失；
- 无法用于安全审计；
- 无法满足管理员长期追溯需求。

## 7. 建议的下一阶段开发路线

### 第 1 阶段：打通数据库单一事实源

目标：消除内存状态，确保所有核心业务数据可持久化。

需要完成：

1. 将任务服务从 `_TASKS` 迁移到 PostgreSQL。
2. 将环境服务从 `_ENVS/_PACKAGES/_JOBS` 迁移到 PostgreSQL。
3. 将审计日志从 `_AUDIT_LOGS` 迁移到 `audit_logs` 表。
4. 将系统设置从 `_SETTINGS` 迁移到 `settings` 表。
5. 清理与数据库模型重复的内存变量。
6. 增加必要的数据库事务与状态变更事件。

### 第 2 阶段：打通任务调度主链路

目标：实现任务从提交到实际运行的闭环。

需要完成：

1. 用户提交任务时写入 `tasks`、`task_requirements`。
2. 调度器扫描 `wait` 状态任务。
3. 调度器根据节点状态、GPU 空闲情况、用户配额选择目标 GPU。
4. 写入 `task_allocations`。
5. 将任务状态改为 `dispatching`。
6. 执行器通过 SSH 调用远端 runner。
7. runner 在目标节点启动任务并写入 PID。
8. 执行器回写任务状态为 `running`。
9. 任务结束后回收 allocation 并写入结束状态。

### 第 3 阶段：实现 Runtime Guard

目标：防止用户通过修改 `CUDA_VISIBLE_DEVICES` 或代码内部指定 GPU 的方式绕过调度。

需要完成：

1. 为每个运行任务建立 guard 记录。
2. 采集任务主 PID 及子进程 PID 树。
3. 通过 `nvidia-smi` 查询每个 PID 实际占用的 GPU。
4. 将实际 GPU UUID 与 `task_allocations` 中分配的 GPU UUID 比对。
5. 如果发现越权使用 GPU，立即终止任务。
6. 将任务状态标记为 `alloc_error`。
7. 前端显示“调度错误”。
8. 写入 `task_events` 和审计日志。

### 第 4 阶段：完善环境维护系统

目标：支持用户在 B/S 架构下维护自己的 Python 环境。

需要完成：

2. 支持 whl 包上传。
3. 支持源码压缩包上传。
4. whl 包走 `pip install`。

7. 继续保留测试与真实 API 不一致的状态。

## 11. 结语

本次检查表明，NebulaGrid 目前已经完成了较多管理面和数据模型设计工作，具备继续开发的基础。

但是，项目真正的核心价值在于：

> 通过纯 B/S 架构，为实验室用户提供稳定的 GPU 任务提交、调度、环境维护、文件管理和运行监管能力。

因此，下一阶段不应优先继续扩展页面，而应集中处理 **任务、环境、设置、审计的数据库固化**，并尽快打通 **提交 → 调度 → 执行 → 守护 → 日志 → 回收** 的最小可用链路。

只要这条主链路打通，NebulaGrid 就可以从“管理后台原型”进入“可运行调度系统 MVP”阶段。
