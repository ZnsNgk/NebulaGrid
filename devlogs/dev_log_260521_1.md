## 1. 本次更新结论

本轮开发继续集中在 **环境管理**，而且相较 2026-05-20 的版本又有明显推进。

上一版环境管理主要完成了：

- 环境本体数据库化；
- conda 环境扫描；
- zip 环境导入；
- 环境副本；
- 环境路径修复；
- 环境权限修复；
- 环境检测；
- 环境日志；
- 前端环境状态轮询。

这一版在此基础上继续推进到 **环境包安装和已安装包管理**：

1. 新增主节点本机离线安装接口；
2. 支持离线安装 conda `.tar.bz2` 包；
3. 支持单 whl 离线安装；
4. 支持 whl 文件夹 + `requirements.txt` 批量离线安装；
5. 支持源码目录 `pip install .`；
6. 支持源码目录 `python setup.py install`；
7. 支持删除已安装包前的预览确认；
8. 支持按包来源生成 `conda remove` / `pip uninstall` 命令；
9. 支持保护 Python、pip、setuptools、conda 等核心包，避免被误删；
10. 新增 `EnvOperationLog` 数据库表，并将环境操作日志同步落库；
11. 前端新增环境包安装抽屉、路径选择器、安装结果展示；
12. 前端新增已安装包删除抽屉、包列表勾选、删除确认和删除结果展示。

因此，当前阶段可以判断为：

> **节点管理、用户管理已经基本成型；文件管理处于收尾阶段；环境管理已经进入中后段，环境本体、导入、检测、复制、日志、本机离线包安装和已安装包删除均已有实现；任务管理仍未正式进入主开发阶段。**

按照当前开发顺序，整体工程完成度可从上一版约 **65%–67%** 提升到约 **70%–72%**。

需要注意的是，当前环境包安装分成两条链路：

1. **本机同步安装链路**：已经可用，直接在主节点目标 conda 环境中执行 conda/pip 命令。
2. **EnvPackage / EnvInstallJob 队列链路**：仍未完全打通，`upload_package()` / `install_package()` 仍使用 `_PACKAGES/_JOBS` 内存变量，`env_install_worker.py` 仍主要是扫描数据库 queued job 并打印数量。

也就是说，环境管理已经具备实际使用价值，但“上传包 → 入库 → 安装 job → worker 消费 → compile 模式”的完整异步链路仍待继续开发。

| zip 环境导入缺压缩炸弹限制 | 可能占满磁盘或 inode | 限制解压总大小、文件数量、最大层级 |
| API 后台线程执行导入/复制 | 大环境导入或复制时稳定性有限 | 后续迁移到独立 worker |
| `list_envs()` 过滤条件需确认 | 手动 registered 环境若未被扫描到，可能不显示 | 建议显示所有可见 `registered/available` 环境 |
| 环境操作日志 DB 已有，但前端主要读文件日志 | 结构化日志检索能力尚未释放 | 后续可加环境操作日志分页查询 |

## 7. 当前最值得肯定的改进

### 7.1 环境包安装开始真正可用

用户现在可以通过 Web 文件管理选择包文件，然后在环境管理页面安装到目标环境中。

支持方式包括：

- conda `.tar.bz2` 离线安装；
- 单个 whl 离线安装；
- whl 文件夹 + requirements.txt 批量安装；
- 源码目录 `pip install .`；
- 源码目录 `python setup.py install`。

这对于主节点不能开放 SSH、且主节点严禁联网的使用场景非常重要。

### 7.2 已安装包删除具备保护机制

当前删除包不是直接根据用户输入拼命令，而是：

1. 先检测目标环境真实包列表；
2. 根据用户选择解析包名；
3. 检查包是否存在；
4. 判断是否属于核心保护包；
5. 按来源生成 `conda remove` 或 `pip uninstall`；
6. 给前端确认文案；
7. 用户确认后才执行删除。

这个设计比直接提供命令输入安全很多。

### 7.3 环境操作日志结构化

`EnvOperationLog` 的加入，使环境操作不再只是文件日志。  
后续可以基于该表实现环境操作历史、安装失败查询、按用户/环境/动作筛选、统计报表等功能。

### 7.4 文件管理与环境管理进一步联动

文件管理现在不仅用于上传脚本和压缩包，还成为：

- 环境 zip 导入入口；
- conda 包选择入口；
- whl 包选择入口；
- requirements.txt 选择入口；
- 源码目录选择入口。

这说明前面的文件管理阶段已经开始支撑环境管理阶段。

## 8. 当前主要风险

| 风险 | 所属阶段 | 影响 | 建议 |
|---|---|---|---|
| 本机安装是同步请求 | 环境管理 | 大包安装会长时间占用 API 请求，失败恢复有限 | 改成 EnvInstallJob + worker |

| `env_install_worker.py` 仍是占位 | 环境管理 | 独立安装队列无法工作 | 实现 normal 模式安装 worker |
| 安装成功未写 manifest | 环境管理 | 无法精确追踪安装文件和回滚 | 写入 `EnvPackageManifest` 或安装记录 |
| 源码安装可能触发联网依赖解析 | 环境管理 | 主节点无网时会失败，或不符合隔离预期 | 加强 `--no-index` 策略或明确提示 |
| 删除包不会自动修复依赖 | 环境管理 | 用户可能破坏环境 | 保留确认，建议增加环境快照或回滚提示 |
| 压缩炸弹检测不足 | 文件/环境管理 | 导入大压缩包可能占满磁盘 | 限制总大小、文件数量、层级 |
| 导入/复制仍在 API 后台线程 | 环境管理 | API 重启会中断，长任务不稳定 | 迁移为独立 worker |
| 上传大小限制如果只靠 Nginx 不够稳 | 文件管理 | 用户可能上传超大文件压垮后端 | 后端也读取配置并强制限制 |
| 任务服务仍是内存 | 任务管理 | 未来调度器看不到任务 | 任务阶段首要迁移 |
| Runtime Guard 尚未实现 | 任务管理 | 用户仍可绕过 GPU 分配 | 任务阶段实现 PID/GPU 检查 |
