# 管理员使用手册

## 1. 管理员负责什么

管理员拥有全局维护权限，负责平台可用性、账号关系、节点资源、任务异常、环境维护和审计追踪。

管理员可以：

- 查看全局节点、GPU、任务和资源状态。
- 管理所有用户、导师学生关系、登录设备和密码。
- 新增、修改、重连、强制下线和删除计算节点。
- 查看、提交、修改、中止、删除和重新提交全局任务。
- 维护文件、共享目录和环境。
- 修改系统设置。
- 查看审计日志，追踪关键操作。

操作原则：

- 危险操作前先确认影响范围。
- 删除、强制下线、停用账号、中止任务等动作应能通过审计解释清楚。
- 优先用页面提供的操作，不直接改数据库或文件。
- 遇到资源异常时，记录节点名、任务号、用户、时间和日志片段。

## 2. 登录、安全与账号自检

1. 使用管理员账号登录。
2. 首次登录后进入 `账号管理` 修改密码。
3. 检查自己的登录设备，陌生设备立即下线。
4. 如需开启 Samba，输入当前密码并确认状态。

管理员第一次接手平台时，建议先做这几项确认：

1. 确认当前账号确实是管理员角色。
2. 确认至少保留两个可用管理员账号，避免唯一管理员忘记密码或被停用后无法维护。
3. 在 `用户管理` 中抽查学生、导师账号是否有正确角色和导师关系。
4. 在 `系统设置` 中确认 Linux 子账户、Samba 账号管理是否符合当前部署策略。
5. 在 `审计日志` 中确认登录、改密、用户维护等关键操作能够被记录。

安全建议：

- 不要共享管理员账号。
- 不要在共享文件夹存放密钥、数据库密码、备份包或账号表。
- 公网或不可信网络部署时，应使用 VPN、防火墙或反向代理访问控制。
- 对异常登录，先下线设备，再停用或重置相关账号。

## 3. Linux 子账户、Samba 与用户远程访问

这一节面向管理员，用于理解用户为什么能 SSH 到自己的账号、为什么 Windows 共享需要先开启 Samba，以及用户连接失败时应该查哪里。普通学生和导师不需要知道后台命令，只需要按各自手册中的步骤连接。

### 后台前置条件

生产环境如果希望用户用平台用户名和密码 SSH 到主节点，或者在 Windows 网络共享中访问个人目录，需要同时满足：

- 主节点已启用 Linux 子账户管理，平台创建学生或导师时会创建同名 Linux 账户。
- 用户个人目录映射到 `NEBULAGRID_USER_HOME_ROOT/<user_name>`，默认部署通常是 `/home/ddltm/data/user/<user_name>`。
- 主节点已安装并运行 `smbd`。
- 主节点 Samba 配置使用 `[homes]` 动态共享，并把路径限制到用户个人目录，例如 `/home/ddltm/data/user/%S`。
- API 运行用户拥有受限的免交互 sudo 权限，用于 `useradd`、`chpasswd`、`smbpasswd`、`pdbedit` 和 `systemctl restart smbd` 等必要命令。
- 防火墙、VPN 或内网策略允许用户访问主节点的 SSH 端口和 Samba 的 445 端口。

不要把 `/home/ddltm`、`/home/ddltm/data` 或共享 SSD 根目录整体暴露成 Samba 共享。NebulaGrid 的 Windows 共享只应暴露登录用户自己的 home；公共资料仍建议通过 Web `共享文件夹` 视图分发。

### 用户开启 Samba 时系统做了什么

用户在 `账号管理` 中开启 Samba 时，会输入当前平台密码。后端会先确认同名 Linux 子账户存在，然后用该密码创建或更新同名 Samba 账号，并重启 `smbd` 让 Windows 尽快看到新状态。

管理员需要理解几个状态：

- `已禁用`：用户没有开启 Samba，Windows 共享不能登录。
- `已启用`：Samba 账号可用，用户可以访问 `\\<master-ip>\<user_name>`。
- `未执行`：当前环境没有执行真实 Samba 命令，常见于开发环境或后台管理开关未启用。
- `失败`：后端尝试执行 Samba 命令失败，需要看 API 日志、sudoers、Samba 配置和系统服务状态。

用户改平台密码或管理员重置用户密码后，已开启 Samba 的用户会同步更新 Samba 密码。未开启 Samba 的用户不会被动创建 SMB 凭据。

### 给用户的连接说明

给学生或导师开通账号时，建议一次性提供这些信息：

- NebulaGrid 登录地址。
- 用户名和初始密码。
- 主节点地址，例如 `192.168.0.1` 或 `master.example.local`。
- Windows 共享地址格式：`\\<master-ip>\<user_name>`。
- SSH 登录格式：`ssh <user_name>@<master-ip>`。
- 首次登录后必须修改密码。
- 训练任务必须通过 `任务管理` 提交，不要在 SSH 中长期直接占用 GPU。

用户在 Windows 中连接共享目录时，应直接访问自己的共享名。例如用户 `test1` 访问：

```text
\\192.168.0.1\test1
```

用户名填写 `test1`，密码填写平台密码。如果 Windows 缓存了旧密码，让用户在 Windows `cmd` 中执行：

```bat
net use \\192.168.0.1\test1 /delete /y
cmdkey /delete:192.168.0.1
net use \\192.168.0.1\test1 /user:test1 *
```

用户 SSH 到自己账号时使用：

```bash
ssh test1@192.168.0.1
```

大文件上传下载可用：

```bash
scp ./dataset.zip test1@192.168.0.1:~/dataset.zip
scp test1@192.168.0.1:~/outputs/result.csv ./result.csv
```

### Samba 和 SSH 排障顺序

用户反馈无法连接 Windows 共享时，按下面顺序排查：

1. 查用户页面状态：账号是否启用，Samba 状态是否 `已启用`。
2. 查用户访问地址：是否写成 `\\<master-ip>\<user_name>`，而不是只写 `\\<master-ip>`。
3. 查 Windows 凭据缓存：让用户清理 `net use` 和 `cmdkey` 后重连。
4. 查网络：用户是否在内网或 VPN，Windows 是否能访问主节点 445 端口。
5. 查服务：主节点 `smbd` 是否运行并监听 445。
6. 查账号：`id <user_name>` 是否存在 Linux 子账户，`pdbedit -L` 是否存在 Samba 账号。
7. 查配置：`testparm` 中 `[homes]` 是否指向用户目录根。
8. 查日志：`journalctl -u nebulagrid-api` 和 `journalctl -u smbd` 是否有 sudo、账号或路径错误。

用户反馈无法 SSH 时，按下面顺序排查：

1. 用户名是否为平台用户名，不是姓名或统一识别码。
2. 用户账号是否启用，密码是否刚被重置。
3. Linux 子账户是否存在。
4. 主节点 SSH 服务是否运行，防火墙是否允许访问。
5. 用户默认 home 目录是否存在，权限是否正确。
6. 如果平台改密后 SSH 仍旧密码，检查 Linux 子账户同步命令和 API 日志。

## 4. 总览与资源判断

`总览` 展示全局资源快照：

- 节点总数、在线节点。
- GPU 总数、可用 GPU。
- 运行任务数量。
- 节点 CPU、可用内存、上传、下载。
- GPU 使用率、显存使用量、调度占用。

资源判断：

- 节点离线时，相关任务可能无法继续。
- GPU 显存高但无对应平台任务时，可能存在平台外进程或状态延迟。
- GPU 可用性列表未配置时，相关 GPU 不会进入任务调度。
- GPU 算力由监控自动探测；旧驱动探测不到时应在节点管理按 index 配置覆盖值。
- 网络或 NFS 异常会表现为任务启动慢、日志缺失、文件不可见。

## 5. 任务管理

管理员可查看所有任务。

任务区域：

- `等待区`：未运行或挂起任务。
- `执行区`：准备中、派发中、运行中任务。
- `历史区`：完成、失败、取消、节点掉线、调度错误等任务。

常用操作：

- `添加任务`：替用户或管理员自己提交任务。
- `批量添加`：批量提交多条命令。
- `修改选中任务`：修改等待、挂起或历史任务；历史任务修改后会重新进入等待或挂起状态。
- `挂起/取消挂起选中任务`：临时暂停或恢复等待任务。
- `删除选中任务`：删除等待或历史记录，可选择是否连带删除后继任务。
- `中止选中任务`：停止运行任务，会影响远端进程和日志。
- `重新提交`：从历史任务生成新任务。
- `查看任务日志`：查看 tail、刷新、下载或复制命令。

任务字段：

- **环境**：运行任务所需 Python/conda 环境。
- **项目路径**：命令执行目录。
- **命令**：单行命令。
- **节点**：可指定节点，也可留空。
- **GPU 型号兼容提示**：选择环境后，可用 GPU 型号以卡片显示。精确命中 `sm_xx` 为绿色“原生支持”；普通 cubin 在同一主版本内从较低次版本向上兼容时为绿色“同主版本兼容”；其余为红色“不支持”。`compute_xx` 只保留为原始探测数据，不参与兼容判断；带 `a`/`f` 等专用 SM 后缀的目标不向更高架构扩展。未指定型号时调度器只过滤红色不支持卡，其他状态不重排；显式型号仍按强制约束调度并完全忽略兼容状态。
- **GPU 数量**：`0` 表示 CPU 任务。
- **GPU 型号**：限制任务只能使用指定型号；只选型号时在可见节点中匹配，只选节点时只在该节点内调度，两者同时选择时只在该节点内匹配该型号。
- **前驱任务**：依赖任务成功后再运行。
- **紧急、复用、挂起**：影响排队和运行策略。

任务未指定节点时，调度器会按用户自有节点、组内共享节点、组内他人公开共享的私有节点、其他公开节点的顺序尝试分配。管理员排查资源分配时，应同时查看任务所有人和节点所有人/共享范围。

批量命令规则：

- 每行一条命令。
- 空行忽略。
- 以 `#` 开头的整行忽略。
- 行内 `#` 后内容作为注释忽略。

任务状态：

- `wait` / 等待：等待资源。
- `on_hold` / 挂起：保存但暂不运行。
- `dispatching` / 派发中：任务正在进入运行前准备阶段。
- `running` / 运行中：远端进程正在执行。
- `succeeded` / 完成：返回码为 0。
- `failed` / 失败：脚本或启动命令返回非 0。
- `cancelled` / 已取消：被用户或管理员中止。
- `offline` / 节点掉线：节点异常导致中断。
- `alloc_error` / 调度错误：实际资源使用和申请资源不一致。
- `lost` / 状态未知：重启或连接异常后无法确认。

## 6. 文件管理

管理员可维护平台可见文件，包括个人目录和共享文件夹。

常用操作：

- 进入目录、上级、刷新。
- 上传、下载、新建文件夹、新建文件。
- 文本文件预览、编辑和保存。
- 重命名、复制、移动、打包 zip、解压压缩包、删除。
- 文件权限面板可为普通文件授予执行权限，用于处理用户上传 `.sh` 后主账户无法直接执行的问题。
- 在个人目录和共享文件夹之间转移资料。

注意：

- 文件操作直接影响用户任务。
- 删除、移动、覆盖保存前确认路径。
- 共享文件夹只放可公开给登录用户的资料。
- 大文件、二进制文件不建议在线编辑。
- 压缩包建议使用 zip、tar、tar.gz、tar.bz2、tar.xz。

文件问题排查：

- `path not found`：路径不存在或用户目录未创建。
- `path is outside shared folder`：路径超出共享目录边界。
- `target already exists`：目标文件已存在。
- `target cannot be inside source directory`：不能把目录复制或移动到自身内部。
- `unsupported archive type`：压缩包格式不支持。
- `Permission denied`：若任务命令直接运行脚本路径，先在文件管理中打开脚本并授予执行权限；仍失败时检查用户目录 ACL 和主账户是否为 `NEBULAGRID_MAIN_LINUX_USER`。

## 7. 环境管理

管理员可查看和维护所有环境。

常用操作：

- `刷新环境列表`：重新加载环境。
- `导入环境`：从用户个人目录中的 conda 环境 zip 导入环境，或扫描并登记已有 conda 环境。
- `检测`：检查 Python、PyTorch、TensorFlow、CUDA、`torch.cuda.get_arch_list()` 和包列表，并同步 `envs` 表中的 PyTorch 兼容性字段。
- `查看日志`：查看环境操作日志。
- `创建副本`：为用户准备独立环境。
- `安装包`：安装 conda 包、pip wheel、本地包、源码包。
- `删除包`：先预览后删除，基础包受保护。
- `删除环境`：删除不再使用的环境。

### 用户导入 zip 环境包

用户从其他电脑导入已有 conda 环境时，管理员应按下面链路排查：

1. 用户在另一台 Ubuntu x86_64/amd64 电脑的 `~/miniconda3/envs` 或 `~/anaconda3/envs` 下，把目标环境目录整体打成 zip。
2. 用户通过自己的 Linux 子账户把 zip 上传到主节点个人目录，例如 `/home/ddltm/data/user/<user_name>/<env_name>.zip`。如果生产环境没有启用 Linux 子账户登录，可由管理员代放到该用户个人目录。
3. 用户在 Web `环境管理` 中点击 `导入环境`，选择个人目录里的 zip。
4. 后端先解压到临时目录，拒绝危险路径和链接，再复制到 `/home/ddltm/envs/miniconda3/envs/<target_env_name>`。
5. 后端修复文本文件中的旧环境前缀，整理权限，然后激活环境运行检测脚本。
6. 检测通过后状态变为 `available`；失败时状态变为错误，用户和管理员应查看环境日志。

平台限制需要提前说明清楚：只支持 Linux x86_64/amd64 的 Anaconda3/Miniconda3 环境包。Linux ARM、MIPS 等其他架构不能使用；Windows 和 macOS 环境包禁止上传。系统会自动检测环境包的可用操作系统和执行情况，非 Linux 或无法在当前 conda 体系中激活的环境会被拒绝或标记为失败，不应手工改库把它设为可用。

### 指定节点编译安装

`安装包` 页面中的 `指定节点编译` 用于把环境安装作业放到主节点或某个计算节点上执行，适合源码包、CUDA 扩展包、需要目标节点工具链的包。它和普通训练任务是两条链路：编译安装会进入 `env_install_jobs`，由环境安装 worker 领取执行，不进入任务等待区。

用户操作链路：

1. 用户进入 `环境管理`，选择环境后点击 `安装包`。
2. 用户选择包来源和安装命令。
3. 用户在 `指定节点编译` 区域点击 `在指定节点`。
4. 后端实时探测主节点和用户可见计算节点，返回 `gcc`、`g++`、`clang`、`nvcc` 与 GPU 清单。
5. 用户选择目标节点和 GPU 可见模式。
6. 用户确认后点击 `执行安装`。
7. 作业写入环境安装日志，页面状态显示 `安装中`。

GPU 可见模式：

- `默认`：不设置 `CUDA_VISIBLE_DEVICES`。
- `CPU`：设置一个不可见 GPU 编号，让 CUDA 程序自然回退到 CPU。
- 指定 `GPU`：把 `CUDA_VISIBLE_DEVICES` 设置为用户勾选的 GPU index 列表。

管理员维护重点：

- 主节点和计算节点必须看到一致的环境路径、用户数据路径和环境安装日志路径。
- 计算节点必须能通过平台主账户 SSH 访问。
- 远端脚本目录中应存在环境安装脚本。
- 目标节点需要安装对应工具链，例如 `gcc`、`g++`、`clang`、`nvcc`。
- 环境安装 worker 应处于运行状态，否则作业会一直排队。
- 同一环境安装或删除包期间会加锁，用户重复提交会失败或提示稍后再试。
- 编译安装可能影响节点 CPU、内存、磁盘 IO 和 GPU 探测，应通过审计日志和环境日志追踪。

排障顺序：

1. 看环境状态是否一直停留在 `安装中`。
2. 看环境日志最后几十行，确认是包依赖问题、编译器缺失、CUDA 错误还是 SSH/NFS 问题。
3. 在 `节点管理` 中确认目标节点在线且用户可见。
4. 确认目标节点上的 `gcc`、`g++`、`clang`、`nvcc` 与页面探测一致。
5. 检查 `nebulagrid-env-install-worker` 是否运行。
6. 检查主节点到目标节点的 SSH、共享路径和远端脚本部署。
7. 如果用户选择了具体 GPU，确认 GPU index 与目标节点实际顺序一致。

环境状态：

- `available` / 可用：可选择运行任务。
- `registered` / 已登记：已纳入平台管理。
- `copying` / 复制中：正在创建副本。
- `importing` / 导入中：正在导入环境。
- `testing` / 检测中：正在执行环境检测。
- `installing` / 安装中：正在安装包。
- `failed` / 失败：最近操作失败，需看日志。

环境维护建议：

- 公共环境少改动，给用户实验时优先创建副本。
- 环境正在复制、导入、检测或安装时，不要重复操作。
- 安装失败先看环境日志，再看包格式、依赖版本和 Python 版本。
- 指定节点编译失败时，同时检查目标节点工具链、SSH、NFS 路径和环境安装 worker。
- 删除环境前确认没有任务仍在使用它。
- 平台内安装、升级或删除 PyTorch 成功后会重新检测并更新环境元数据；未安装 PyTorch 时对应版本字段为空、架构列表为空。删除环境时这些同表字段自动一起删除。
- 从旧版本升级后，对数据库中原有环境逐个点击一次 `检测`，回填 PyTorch 版本、CUDA 和架构列表；新发现、导入或复制的环境会自动写入。

## 8. 节点管理

进入 `管理员后台`，切换到 `节点管理`。

新增或修改节点时填写：

- **节点名称**：页面展示名，应稳定唯一。
- **IP 地址**：计算节点地址。
- **SSH 用户**：平台连接节点使用的用户。
- **与主节点最大连接带宽**：用于展示和辅助判断传输能力。
- **GPU 可用性列表**：按 `nvidia-smi` 顺序逐行填写 `0` 或 `1`，`1` 表示该 GPU 可调度，`0` 表示不调度。
- **GPU 算力覆盖列表**：按 `nvidia-smi` index 逐行填写 `major.minor`，如 `8.9`；空行使用监控自动探测值，中间空行必须保留以免 index 错位。
- **使用权**：公开或私有。
- **共享**：不共享、组内共享或公开共享。
- **所有人**：私有或组内共享节点的归属用户。

GPU 数量、型号、UUID、显存和 Compute Capability 由节点监控自动扫描写入数据库。算力查询独立执行，因此旧驱动不支持 `compute_cap` 时不会影响基础 GPU 清单；管理员覆盖值优先于自动探测值。主节点会为每个可监控计算节点保持一条 SSH 长连接，在计算节点上执行远端 `monitor.py --loop --interval <秒数>`；某次扫描发现 GPU 数量变化时，系统会按新的 `nvidia-smi` 顺序更新数据库清单；未在可用性列表中配置的 GPU 默认不参与调度。

监控长连接因网络波动断开时，节点会先显示为离线，再显示为重连中；如果 SSH 连接仍存在但超过 `monitor.watchdog_timeout_seconds` 没有收到有效状态 JSON，也会先标记离线并触发同一套重连流程。自动重连次数由 `系统设置` 中的 `monitor.reconnect_attempts` 控制，默认 3 次；无输出 watchdog 默认 600 秒。每次自动重连都会写入审计日志，次数耗尽后节点保持离线，直到管理员点击 `重连`。

操作说明：

- `修改`：更新节点信息、GPU 可调度开关和可选算力覆盖。
- `强制下线`：用于断电、拔卡、维护、异常进程或节点不可用时；系统会把节点标记为 `offline`、关闭调度、强行终止该节点上的运行任务，并立即释放该节点所有未释放的 GPU 调度占用。
- `重连`：节点恢复后重新建立监控长连接并采集状态；强制下线的节点不会被监控自动拉回在线，必须由管理员显式重连。
- `删除`：移除节点配置，删除前确认任务和审计线索是否还需要保留。

节点排查：

- 节点离线：检查网络、SSH、NFS、账号、驱动、`nvidia-smi`，再看 `nebulagrid-node-monitor` 日志中该节点长连接是否退出，或是否出现 watchdog timeout。
- GPU 数量或型号不对：检查节点监控服务和远端 `monitor.py`，先手动运行单次 JSON 输出，再用 `monitor.py --loop --interval 5` 确认能持续输出；同时确认 `nvidia-smi` 输出正常。
- GPU 算力为空或错误：运行 `nvidia-smi --query-gpu=index,name,compute_cap --format=csv,noheader`；旧驱动不支持时在节点修改页按 index 填写算力覆盖列表。
- 用户看不到节点：检查使用权、共享范围、所有人和导师学生关系。
- 任务总是不分到某节点：检查节点是否在线、调度是否允许、GPU 可用性列表是否把目标 GPU 标为 `1`。

## 9. 用户管理

进入 `管理员后台`，切换到 `用户管理`。

可创建角色：

- **学生**：普通实验用户。
- **导师**：可管理自己名下学生。
- **管理员**：全局维护用户。
- **展示用户**：只进入展示大屏。

创建账号字段：

- 统一识别码。
- 用户名。
- 姓名。
- 角色。
- 导师关系，学生最多两名导师。
- 状态。
- 初始密码，至少 8 位。

编辑账号可修改：

- 用户名。
- 姓名。
- 角色。
- 导师关系。
- 启用或停用状态。

注意：

- 不要删除最后一个管理员。
- 停用账号前确认是否有关键任务正在运行。
- 删除账号前确认文件、环境、任务、导师关系和审计需要。
- 重置密码后提醒用户登录后自行修改。

## 10. 登录管理

进入 `管理员后台`，切换到 `登录管理`。

可以：

- 查看当前在线用户。
- 查看在线设备数、IP、设备和最后活跃时间。
- 按统一识别码、用户名或姓名查询某个用户登录设备。
- 下线指定设备。

处理异常登录：

1. 记录用户、IP、设备和时间。
2. 下线异常设备。
3. 视情况停用账号或重置密码。
4. 查看审计日志确认近期敏感操作。

## 11. 系统设置

进入 `管理员后台`，切换到 `系统设置`。

使用方式：

1. 选择配置键。
2. 阅读说明。
3. 按类型修改配置值。
4. 保存后刷新页面观察效果。

注意：

- 修改可能影响任务、文件、环境、登录或展示大屏行为。
- 节点监控相关键包括 `monitor.interval_seconds`、`monitor.reconnect_attempts` 和 `monitor.watchdog_timeout_seconds`；修改后监控 worker 会在下一次同步目标时替换对应节点线程。
- 生产环境修改关键配置前，应先确认回滚方式。
- 修改后建议查看审计日志，确认操作已记录。

## 12. 审计日志

进入 `管理员后台`，切换到 `审计日志`。

可按以下条件查询：

- 分类。
- 动作。
- 关键词。
- 开始时间。
- 结束时间。

排障时重点记录：

- 操作者。
- 动作。
- 对象类型和 ID。
- 时间。
- 结果。

审计用途：

- 追踪谁创建、修改、删除了用户。

- 还原问题发生前后的操作顺序。

## 13. 推荐运维流程

### 日常巡检

1. 看 `总览`：在线节点、GPU、运行任务是否正常。
2. 看 `管理员后台` 总览：用户、节点、在线用户、审计概况。
3. 进入 `节点管理` 检查离线节点。
4. 进入 `任务管理` 检查长时间等待、失败或节点掉线任务。
5. 进入 `审计日志` 查看近期高风险操作。

### 新用户入组

1. 创建学生或导师账号。
2. 学生绑定导师。
3. 告知初始密码和登录地址。
4. 提醒用户首次登录后改密码。
5. 根据需要分配私有节点或共享资料。

### 新节点上线

1. 确认节点网络、SSH、驱动、GPU 和共享目录。
2. 在 `节点管理` 新增节点。
3. 点击 `重连` 或等待已有监控长连接按 `nvidia-smi` 顺序自动扫描 GPU 数量、型号和算力，并按实际顺序填写 GPU 可用性列表；算力未探测到时再填写覆盖列表。
4. 设置使用权、共享范围和所有人。
5. 保存后观察总览中的节点状态和 GPU 信息。
6. 提交小任务验证运行链路。

## 14. 常见问题排查

### 用户无法登录

- 检查账号是否启用。
- 检查密码是否正确，必要时重置。
- 检查是否存在异常登录设备。
- 检查后端认证服务是否正常。

### 用户看不到节点

- 检查节点是否在线。
- 检查节点使用权和共享范围。
- 检查私有节点所有人。
- 检查导师学生关系。

### 任务一直等待

- 检查是否有在线节点。
- 检查节点是否允许任务进入。
- 检查 GPU 数量、GPU 型号约束、指定节点和可用性列表是否满足。
- 检查前驱任务是否成功。
- 检查任务是否挂起。
- 检查用户是否指定了离线节点。

### 任务运行后失败

- 先看任务日志。
- 再看环境日志和环境检测结果。
- 检查项目路径、命令、数据文件、输出目录。
- 检查 CUDA、PyTorch、TensorFlow 版本。
- 对照环境 `pytorch_arch_list` 中的 `sm_xx` cubin 和 GPU 有效算力；`compute_xx` 不参与判断。卡片颜色用于说明兼容等级，未指定型号时红色卡会被过滤，用户显式强制选择后则仍会照常分配。
- 检查节点是否掉线或 NFS 异常。

### 任务出现调度错误

- 查看任务申请的 GPU 数量、GPU 型号、指定节点和实际分配 GPU。
- 查看实际运行节点和 GPU。
- 检查命令是否绕过资源限制。
- 检查是否有平台外进程占用 GPU。
- 必要时强制下线节点并清理异常进程。

### 节点离线

- 检查网络连通性。
- 检查 SSH 登录。
- 检查 NFS 挂载。
- 检查 NVIDIA 驱动和 `nvidia-smi`。
- 检查远端监控脚本。
- 检查 `monitor.watchdog_timeout_seconds` 是否过短，导致远端脚本偶发慢帧被误判为离线。
- 节点恢复后点击 `重连`。

### 文件操作失败

- 检查路径是否存在。
- 检查目标是否已存在。
- 检查是否试图操作受保护根目录。
- 检查压缩包格式。
- 检查共享目录和用户目录权限。

### 环境操作失败

- 查看环境日志。
- 检查环境是否正在复制、导入、检测或安装。
- 检查包格式和依赖版本。
- 检查 Python 版本。
- 对多人共用环境，优先创建副本再处理。
