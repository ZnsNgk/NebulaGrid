# NebulaGrid 3.0 生产联调测试文档

**文件名**：`nebulagrid_test_plan_260523.md`  
**日期**：2026-05-23  
**适用版本**：`NebulaGrid-0523_4.zip`  
**测试阶段**：主题功能开发完成后的生产环境联调联试  
**适用场景**：实验室 / 课题组内部 GPU 集群管理系统  
**目标规模**：几名导师、几十名学生、若干计算节点  
**核心链路**：用户 → 文件/共享目录 → 环境 → 任务 → 调度 → 执行 → 日志 → Runtime Guard → 回收

## 0. 测试说明

### 0.1 测试目标

本文档用于指导 NebulaGrid 进入生产环境前后的联调测试。测试目标包括：

1. 验证主节点、计算节点、NFS、PostgreSQL、InfluxDB、Redis、Nginx、Samba、systemd 等基础设施是否可用。
2. 验证节点管理、用户管理、文件管理、环境管理、任务管理五个核心模块是否形成完整闭环。
3. 验证管理员、导师、学生、展示用户四类角色的权限边界是否正确。
4. 验证 GPU 任务是否可以从 Web 页面提交、调度、远端执行、实时查看日志、完成后回收。
5. 验证 Runtime Guard 是否可以识别用户绕过调度使用未分配 GPU 的行为。
6. 验证 Samba、共享文件夹、scp/NFS 文件路径和 Web 文件管理之间是否协同工作。
7. 为后续试运行提供明确的测试记录和验收标准。

### 0.2 结合实际部署场景后的测试口径

本系统主要用于实验室或课题组内部，用户是可信或半可信成员，规模约为几名导师和几十名学生。因此测试优先级按照实际风险调整：

| 项目 | 测试口径 |
|---|---|
| 大文件传输 | 建议使用 `scp`，不把 Web 文件管理作为数据集传输主通道 |
| 文件管理页面 | 主要测试脚本、配置、小文件、压缩包、日志、共享文件夹 |
| 压缩炸弹 | 不作为上线阻塞项，只做基础路径安全和异常处理测试 |
| 环境包安装/删除 | 用户对自己的环境负责，重点测试可用性和日志，不强制要求精细 manifest |
| 多租户恶意攻击 | 非公网多租户场景，不作为首轮联调重点 |
| 性能压测 | 不做互联网级压测，只做实验室规模并发测试 |
| 审计 | 用于排查和追溯，不按金融级合规审计要求测试 |

### 0.3 测试优先级定义

| 优先级 | 含义 | 是否阻塞试运行 |
|---|---|---|
| P0 | 核心链路，失败后系统无法进入试运行 | 阻塞 |
| P1 | 重要功能，失败会明显影响实验室使用 | 通常阻塞，视场景判断 |
| P2 | 增强功能或边界场景，失败可记录后修复 | 不阻塞 |
| P3 | 后续优化项 | 不阻塞 |

# 1. 基础部署与服务联通测试

## DEP-01：后端健康检查

**优先级**：P0  
**测试目标**：确认 API 服务已启动，统一响应格式正常。

**前置条件**：

- 后端服务已启动。
- Nginx 或直接 uvicorn 端口可访问。

**测试步骤**：

1. 在浏览器访问：

   ```text
   http://<MASTER_IP>/api/health
   ```

2. 或在主节点执行：

   ```bash
   curl -s http://127.0.0.1:<API_PORT>/api/health | jq
   ```

**预期结果**：

- HTTP 状态码为 `200`。
- JSON 中 `ok` 为 `true`。
- `data.status` 为 `ok`。
- 响应中存在 `request_id`。

**通过标准**：

- 以上结果全部满足即通过。
- 如果 API 端口无法访问，阻塞后续所有 Web 测试。

---

## DEP-02：PostgreSQL 连接与数据库表检查

**优先级**：P0  
**测试目标**：确认数据库可连接，关键表已创建。

**前置条件**：

- PostgreSQL 服务已启动。
- `.env` 中 `NEBULAGRID_DATABASE_URL` 配置正确。
- 已执行数据库初始化脚本。

**测试步骤**：

1. 在主节点执行：

   ```bash
   cd <NebulaGrid>/backend
   python scripts/init_db.py
   ```

2. 使用 psql 检查关键表：

   ```bash
   psql "$NEBULAGRID_DATABASE_URL" -c "\dt"
   ```

3. 确认至少存在以下表：

   ```text
   users
   login_sessions
   nodes
   gpus
   envs
   env_packages
   env_install_jobs
   tasks
   task_requirements
   task_allocations
   task_runtime_guards
   audit_logs
   settings
   file_jobs
   env_operation_logs
   ```

**预期结果**：

- 初始化脚本无异常。
- 所有关键表存在。
- `users` 表中存在默认管理员或已创建管理员。
- `settings` 表中存在默认配置。

**通过标准**：

- 数据库可连接且关键表齐全。

## DEP-04：InfluxDB bucket 与写入权限检查

**优先级**：P0  
**测试目标**：确认节点/GPU 指标可以写入 InfluxDB。

**测试步骤**：

1. 确认环境变量：

   ```bash
   echo "$NEBULAGRID_INFLUXDB_URL"
   echo "$NEBULAGRID_INFLUXDB_ORG"
   echo "$NEBULAGRID_INFLUXDB_BUCKET"
   ```

2. 使用 Influx CLI 或 Web UI 检查 bucket 是否存在。
3. 启动 node monitor 后，查询最近指标：

   ```bash
   influx query '
   from(bucket: "nebulagrid_metrics")
     |> range(start: -10m)
     |> limit(n: 10)
   '
   ```

**预期结果**：

- bucket 存在。
- token 具有写入和读取权限。
- monitor 运行后能看到 `node_metrics` 或 `gpu_metrics`。

**通过标准**：

- InfluxDB 能写入并查询指标。
- 如果大屏无法显示历史曲线，优先检查本项。

## DEP-06：Nginx SSE 禁缓冲检查

**优先级**：P1  
**测试目标**：确认任务日志实时推送不被 Nginx 缓冲。

**前置条件**：

- 已有运行中任务，且任务持续输出日志。
- 前端任务日志面板使用 SSE 或浏览器 EventSource。

**测试步骤**：

1. 提交一个每秒输出一行日志的任务：

   ```bash
   python -u -c "import time; [print(f'line {i}', flush=True) or time.sleep(1) for i in range(60)]"
   ```

2. 打开任务日志面板。
3. 观察日志是否每秒刷新。
4. 如果没有刷新，使用 curl 测试：

   ```bash
   curl -N -H "Authorization: Bearer <TOKEN>" \
     http://<MASTER_IP>/api/tasks/<TASK_ID>/log/events
   ```

**预期结果**：

- 日志应接近实时出现。
- 不应等任务结束后一次性输出。

**通过标准**：

- Web 页面或 curl 中能持续收到日志增量。
- 若失败，不阻塞任务执行，但影响体验，应调整 Nginx SSE 禁缓冲配置。

## DEP-10：NFS 共享路径一致性

**优先级**：P0  
**测试目标**：确认主节点和计算节点看到相同的 `/home/ddltm/data`、`/home/ddltm/envs`、`/home/ddltm/shared`。

# 2. 用户、权限、Linux 账号与 Samba 测试

- 当前用户角色为 `admin`。
- 权限列表包含节点、用户、文件、环境、任务、后台相关权限。

**通过标准**：

- 管理员可正常访问所有管理页面。

**优先级**：P0  
**测试目标**：验证管理员可创建导师账号。

**测试步骤**：

1. 管理员进入用户管理。
2. 创建用户：

   ```text
   用户名：mentor-a
   姓名：导师A
   角色：导师
   状态：启用
   ```

## USER-03：创建学生并绑定导师

**优先级**：P0  
**测试目标**：验证学生最多可绑定两名导师，导师可管理自己学生。

**测试步骤**：

1. 管理员创建学生 `student-a1`。
2. 选择导师 `mentor-a`。
3. 保存后切换到导师账号登录。
4. 进入学生管理页面。
5. 查看是否能看到 `student-a1`。
6. 再创建另一个学生，不绑定 `mentor-a`，验证导师不可见。

**预期结果**：

- `mentor-a` 可以看到并管理 `student-a1`。
- `mentor-a` 看不到非自己名下学生。
- 如果选择超过两名导师，后端应拒绝。

**通过标准**：

- 导师-学生权限边界正确。

## USER-04：账号停用

**优先级**：P0  
**测试目标**：验证停用账号后不能登录，已有会话失效。

**测试步骤**：

1. 使用学生账号登录，保持浏览器不退出。
2. 管理员在用户管理中停用该学生。
3. 学生刷新页面或访问任意 API。
4. 学生尝试重新登录。

**预期结果**：

- 旧会话失效。
- 页面提示未登录或账号不可用。
- 重新登录失败，提示账号已停用。
- 如果该用户开启了 Samba，应同步禁用 Samba。

**通过标准**：

- Web 会话和登录入口均阻止停用用户继续使用。

---

## USER-05：重置密码和会话吊销

**优先级**：P0  
**测试目标**：验证管理员重置密码后，旧 token 失效，新密码可登录。

**测试步骤**：

1. 学生登录系统。
2. 管理员重置学生密码。
3. 学生原浏览器刷新。
4. 学生用旧密码登录。
5. 学生用新密码登录。

**预期结果**：

- 原会话失效。
- 旧密码登录失败。
- 新密码登录成功。
- 如果用户开启 Samba，Samba 密码同步更新。

**通过标准**：

- 密码重置和会话吊销一致。

---

## USER-06：用户自助修改密码

**优先级**：P1  
**测试目标**：验证当前用户可修改自己的密码，并同步会话和 Samba。

**测试步骤**：

1. 学生登录。
2. 进入账号管理。
3. 输入当前密码和新密码。
4. 修改成功后退出。

# 7. Runtime Guard 测试

## GUARD-01：正常任务不误杀

**优先级**：P0  
**测试目标**：验证正常使用分配 GPU 的任务不会被 Runtime Guard 误杀。

**测试步骤**：

1. 提交单 GPU 任务。
2. 任务中只使用 `CUDA_VISIBLE_DEVICES` 指定的 GPU。
3. 任务持续运行 2–5 分钟。
4. 查看 guard 状态和任务状态。

**预期结果**：

- guard 不记录 violation。
- 任务不被终止。
- 最终 succeeded。

**通过标准**：

- 正常任务不误杀。

---

## GUARD-02：越权使用未分配 GPU

**优先级**：P0  
**测试目标**：验证用户绕过调度使用其他 GPU 时触发 `alloc_error`。

**前置条件**：

- 节点至少 2 张 GPU。
- 调度器给任务分配 1 张 GPU。
- GPU UUID 已同步。

**测试命令示例**：

```bash
python -u - <<'PY'
import os, time, subprocess
print("assigned CUDA_VISIBLE_DEVICES:", os.environ.get("CUDA_VISIBLE_DEVICES"), flush=True)
# 故意覆盖为另一张 GPU。实际测试时根据节点 GPU 数调整。
os.environ["CUDA_VISIBLE_DEVICES"] = "1"
import torch
x = torch.randn(4096, 4096, device="cuda")
print("using cuda", x.device, flush=True)
time.sleep(300)
PY
```

**测试步骤**：

1. 提交任务，要求 1 张 GPU。
2. 等任务进入 running。
3. 等待 Runtime Guard 扫描。
4. 查看任务状态、事件、日志和 guard 摘要。

**预期结果**：

- Runtime Guard 发现实际 GPU UUID 不在 allocation 中。
- 第一次可记录 warning。
- 连续确认后终止进程组。
- 任务状态变为 `alloc_error`。
- 前端显示调度错误。
- allocation 释放。

**通过标准**：

- 越权 GPU 使用被检测并终止。

---

## GUARD-03：子进程越权检测

**优先级**：P0  
**测试目标**：验证 Runtime Guard 会检查任务 PID 树，而不是只检查根进程。

**测试步骤**：

1. 提交一个 shell 或 Python 脚本。
2. 主进程启动子进程，子进程使用未分配 GPU。
3. 观察 guard 行为。

**预期结果**：

- Runtime Guard 能从 root_pid 展开子进程。
- 子进程 GPU 使用被识别。
- 越权时进入 `alloc_error`。

**通过标准**：

- 子进程 GPU 越权不会漏报。

---

## GUARD-04：GPU UUID 缺失处理

**优先级**：P1  
**测试目标**：验证 GPU UUID 未同步时系统不会误杀。

**测试步骤**：

1. 临时构造或模拟某 GPU allocation 缺少 UUID。
2. 运行任务。
3. 观察 guard 状态。

**预期结果**：

- guard 进入 uuid_pending 或类似状态。
- 不应误杀任务。
- 日志提示需要 monitor 同步 GPU UUID。

**通过标准**：

- UUID 缺失时系统行为保守且可诊断。

---

## GUARD-05：任务取消时 guard 回收

**优先级**：P1  
**测试目标**：验证取消任务后 Runtime Guard 不再反复扫描已结束任务。

**测试步骤**：

1. 提交长时间 GPU 任务。
2. 任务 running 后取消。
3. 等 executor 回收。
4. 查看 guard 状态。

**预期结果**：

- 任务 cancelled。
- guard 状态结束或不再 active。
- 不产生持续错误日志。

**通过标准**：

- guard 生命周期随任务结束而收敛。
